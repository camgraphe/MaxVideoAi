Périmètre : code courant, configuration Supabase hébergée, variables Vercel Production, DNS publics et diagnostic SMTP sans envoi. Constat initial avant migration ; voir le complément final pour la bascule SMTP effectuée ensuite. Aucun abonnement souscrit.

## Constats prioritaires

1. **P0 — Récupération bloquée par Postmark.** Le journal Supabase du 21/09/2026 à 12:32:07 UTC (14:32:07 à Madrid) contient `POST /recover`, HTTP 500, `unexpected_failure`, SMTP `535 5.7.8 authentication failed` pour le compte signalé. Le SMTP hébergé utilise `smtp.postmarkapp.com:587`. L'envoi échoue avant livraison : aucun élément ne désigne le dossier spam. La raison de l'invalidité du secret (rotation, mauvais jeton, révocation…) reste inconnue.
2. **P0 — Étape de changement de mot de passe absente.** `sendReset` dirige vers le callback générique, qui ouvre `next`. Aucun écran de nouveau mot de passe ni appel `updateUser({ password })` n’existait dans le code initial audité. Le correctif local ajoute maintenant cette étape dédiée (non déployée). Réparer le SMTP seul est insuffisant.
3. **P1 — Erreur opaque.** Le SDK Auth installé sérialise certaines réponses HTTP 500 sous forme `{}` ; le contrôleur affichait `error.message` directement. Correction locale : messages EN/FR/ES, rejets réseau/chargement traités, limites de débit distinguées, double envoi bloqué et succès formulé sans révéler l'existence d'un compte.
4. **P1 — Configuration dispersée.** Supabase utilise Postmark, l'application Brevo, Vercel conserve aussi une clé Resend. Les MX sont Google, contrairement à l'ancien guide Cloudflare. La carte maintenue est désormais dans `stack.md`.
5. **P1 — Pas de suivi de livraison unifié.** Les appels applicatifs attendent l'acceptation SMTP mais n'enregistrent pas d'état livré/rebondi. Aucun webhook e-mail actif trouvé. `email_events` existe seulement comme schéma historique. Un succès SMTP ne prouve pas la réception.
6. **P1 — Langue des e-mails.** Le modèle Recovery hébergé est l'anglais par défaut. Les paramètres de redirection ne traduisent pas automatiquement ce modèle.

- Les variables Brevo et contact existent en Production. Les variables optionnelles `LEGAL_NOTIFY_EMAIL`, `INFRA_COST_ALERT_EMAIL_TO` et `SLACK_WEBHOOK_URL` ne figurent pas dans la liste Production consultée : ne pas présumer ces alertes actives.
- La connexion SMTP avec les identifiants locaux Brevo fonctionne via TLS, sans envoi. La tentative isolée avec `vercel env run -e production` ne restitue pas le mot de passe SMTP : elle ne permet donc pas de vérifier les identifiants déployés. Ne pas confondre ce secret inaccessible avec une authentification refusée en production. La livraison réelle reste non vérifiée.

Accueil : quatre e-mails transactionnels/automatisés sur sept jours, 100 % indiqués délivrés, aucun bloqué/hard bounce sur cette période. SMTP affiché : `smtp-relay.brevo.com:587`, une clé existante active, utilisée le 21 septembre. ## Recommandation

Consolider les e-mails transactionnels sur **Brevo**, déjà intégré, sous réserve de valider compte, quotas, domaine et livraison. Garder Supabase comme propriétaire des jetons/sessions Auth et lui fournir un accès SMTP Brevo dédié. Garder Google pour les boîtes entrantes. Aucun nouveau prestataire nécessaire si le compte Brevo existant satisfait ces contrôles.

Séparer identifiants Auth/applicatifs, expéditeurs et trafic marketing. Si Brevo ne convient pas, réparer Postmark reste possible : les journaux incriminent les identifiants actuels, pas la qualité du fournisseur. Éviter une bascule automatique silencieuse entre plusieurs prestataires.
