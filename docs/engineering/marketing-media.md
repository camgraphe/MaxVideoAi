# Marketing media ownership

The admin library at `/admin/marketing-media` owns independent site copies of generated videos. One publication uses the existing video ID, with any number of gallery/homepage placements. Customer jobs, outputs, assets, billing and quota ownership are unchanged.

## Copy and reuse

`server/marketing-media/snapshot.ts` captures the versioned generation snapshot and a deduplicated manifest of original video, preview, poster, keyframes and reference media. The effective image-output fallback poster is captured and fingerprinted with the source; it remains independent after personal outputs are removed. Model-specific nested media values are included even when their field names do not end in `url`. Complete settings are mandatory; provider interaction dependencies cannot be silently substituted. Prompts and model parameters retain their values. Private owner/asset IDs and billing/provider execution records never enter the public recreation DTO. Source provenance stays in the admin-only database row.

`copy.ts` claims one leased attempt, copies bounded original bytes into `marketing-media/<copy UUID>/<content hash>.<extension>`, verifies public readability, then atomically makes the publication ready after rechecking the exact source. Limits are 64 source files, 256 MiB per file, 512 MiB total and a three-minute preparation deadline. An admin must confirm permission for another owner's video and its references. No generation or charge occurs. Failed preparations are retryable and never replace a public source. Interrupted files remain within the copy's namespace; deletion cleans that namespace, including files from failed attempts.

Readiness uses `server/media/public-http-readiness.ts`, shared with the public-rendition tooling. It requires HEAD size/type plus bounded 206 GETs with exact Content-Range, length and bytes at the beginning and end of the copied file. Redirects, incomplete/oversized ranges, mismatched bytes and timeouts fail preparation. These checks do not transcode or replace full browser/decode qualification. Copy size limits are operation bounds, not public playback budgets; retain originals and explicitly prepare lightweight playback derivatives where needed.

Ready copies are publicly readable storage objects. Publication visibility controls their appearance on the site. Reference grants require exact membership in a ready manifest; private publications allow reuse only for admins. No arbitrary internal storage prefix grants access.

`recreationSnapshot` is separate from the personal job. Normal `/app?from=<original ID>` reuse loads it without a later private-job request overwriting the copied references. Existing comparison links with `remix=1` retain their selected text-to-video settings. Current pricing/availability still applies at generation time. Typed references in older/API snapshots resolve to the active model's input schema when explicit UI slots are absent.

The public recipe retains the explicit video `operation` alongside `inputMode`; the mode alone cannot distinguish Kling Reference/Edit or H3 Recast/Relight. Private source job/output bindings remain excluded, so owned-generation workflows still require the visitor to select an eligible personal source. For older copies that omitted the operation, the server read projection recovers only its known enum from the private source snapshot when the recorded engine and mode match the public publication. Row normalization validates that operation against the model/mode and fills only the missing public operation. Private provenance, references and source IDs never join the public recipe, and no database repair or inference from model/mode is performed.

`public-recreation.ts` removes private job/output/asset/owner bindings recursively from public recipes, including `advanced.extraInputValues.source_job_id` and typed references, in both camelCase and snake_case forms. Publication and public row normalization share this rule so earlier copies are safe on read. Literal text, operation metadata, portable media and creative controls remain intact; private `source_snapshot` and personal `settings_snapshot` are unchanged.

Selected public references are adopted through the measured, account-owned import described in [workspace settings handoff](workspace-settings-handoff.md). A ready public manifest grants only its exact copied URLs and bytes; the original `sourceUrl`, a private publication or a public output’s legacy personal settings cannot grant its inputs.

`public-pricing.ts` removes complete `lumaSource` and `fluxDraftSource` receipt bindings from new publications and public video projections, including earlier copies. Historical amounts, itemization and pricing metadata remain available; personal receipts are unchanged. Current example prices still derive their scenario from the recorded creative settings and a fresh tariff quote.

Curated signed-in and guest job feeds retain this scalar mode/operation metadata without loading complete recipes for every card. Guest job detail verifies starter membership and current public visibility before reading the selected public `recreationSnapshot`; it never returns the personal `settingsSnapshot`. Signed-in personal job reads retain their existing ownership boundary. These handoffs carry creative settings, not a trusted generation price; current example prices and workspace quotes keep their existing canonical recalculation owners.

## Public compatibility

`marketingVideoReader` is used only by public/editorial read owners. It overlays ready publications over the existing `app_jobs` identity in the same SQL request. Personal activity, billing, job reads and private share tokens keep their own owners. No public page route, video ID, redirect, canonical slug, hreflang, editorial approval or sitemap publication rule changes. Output dimensions are retained independently of personal output rows.

`marketingCatalogReader` gives the catalog a narrow `catalog_jobs` relation for membership, eligibility, counts and ordering. It unions independent ready publications by `video_id`, including after personal-source removal, and excludes retired identities. The normal overlay hydrates only the selected page in that same database snapshot. Deserialize each publication once through a lateral record projection, not repeated composite expansion. `BASE_SELECT` omits the complete recreation recipe; the single-video app reader uses `BASE_SELECT_FOR_REUSE`, while SEO detail readers retain their settings projection. Do not remove recipe availability from reuse to reduce list payloads.

Existing admin visibility, thumbnail and removal endpoints target the marketing publication when present. An unfinished preparation returns a conflict in those moderation actions; finish or remove it in the marketing library first. Cleaning up an attempt that never became ready deletes only its copy namespace and attempt row, preserving the original's visibility and placements even during cleanup. Customer indexing preferences must not remove marketing playlist membership. A deleted, previously ready marketing identity remains a tombstone so the old public personal job cannot reappear accidentally. Its authenticated owner can still reuse their surviving personal original; guests and other accounts cannot bypass the retired publication through that fallback.

The placement indicator inventories saved playlists/curations, homepage sections, editorial watch records, public catalog eligibility and registered authored demo sources. It is conservative: a saved but temporarily hidden explicit placement still blocks deletion. Remove placements and unpublish before deleting. Placement guards reject stale writes that reference deleting/deleted publications, including editorial approvals, while allowing an editorial record to be disabled. Curation saves lock the marketing projection alongside their existing source locks.

Promotion of an original registered in `config/public-video-sources.json` is rejected until an explicit migration preserves its prepared playback renditions. Authored URLs in that registry, homepage assets and model/family configurations are not rewritten. Those original sources and their prepared renditions must be retained until a separate explicit migration verifies the exact reader, immutable derivative policy, HTTP/Range behavior and performance. This feature does not introduce customer physical purging or a bulk migration of existing site content.

The guard compares both URLs through the existing `normalizeMediaUrl` contract, including the configured bucket's global/regional S3 aliases. Do not compare raw strings or match paths across arbitrary hosts. Signed queries retain their identity; do not strip credentials or change source URLs in the stored recipe.

## Activation and rollback

1. Follow `docs/deployment/github-vercel.md`: isolated branch, reviewed PR, required Quality CI, current main and normal Git deployment. This implementation does not apply production schema or deploy production.
2. Apply `neon/migrations/78_marketing_media.sql` explicitly to the application Neon database after existing playlist/homepage migrations. It adds the independent table and non-mutating placement guards; it copies no customer media. Replaying it installs guards on optional placement tables added later.
3. Set server-side `MARKETING_MEDIA_ENABLED=1` only after schema installation. The default is disabled; disabled public reads need no new table. Test an admin-owned video first, including reference reuse and public reader identity.
4. Before broad use, verify both production domains against the merged source, storage public GET/HEAD/Range behavior for this namespace, admin authorization and the existing SEO audit. Qualify a real copied publication in the public reader at mobile/desktop widths, including poster optimization, zero original-video requests before Play, first frame, seeking and comparable loading measurements. Do not hide build/CI failures or bypass the deployment policy.

Disabling the flag returns to legacy reads. After a personal source has been removed, disabling the projection cannot preserve that marketing publication; restore the source or keep the projection active while rolling back the admin UI. Do not drop the table or delete copied files as a rollback shortcut. Deleted identity tombstones and completed publications are durable site data.

## Verification

Focused tests cover byte preservation and bounds, exact prompt/settings/reference capture, permission, concurrent attempts, failed-copy retry, source changes/deletion, enabled/disabled public reads, placement-protected deletion and stale writes. Disposable PostgreSQL tests exercise the real catalog and approved watch slug after source deletion. Browser fixtures mount the real admin component at mobile/desktop widths and check retry, reuse links, placement controls and zero original-video requests before Play. Existing watch/SEO, share, curation, workspace and owned-media contracts remain part of validation.

Tests using PostgreSQL may be run with `--test-concurrency=1` on local macOS to avoid exhausting its shared-memory IDs. Use the repository PG17 resolver; do not override version checks. Browser fixtures and offline tests are not a production rollout or live Google Search Console verification.
