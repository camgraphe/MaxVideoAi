# MCP Audio integration

Audio reuses the web runtime and canonical billing policy. It does not create a separate provider pipeline or ledger. Focused preparation and confirmation services own the private execution boundary, while thin MCP adapters publish discovery and exact confirmation only after the paid and Audio publication gates both qualify.

## Requests and discovery

`agent-api/audio-normalization.ts` owns the version-1 `surface: audio` request. Mode and engine must match the actual Audio pack configuration; output count is one. Its settings use the existing Audio semantic validator, preserving scripts, structured lyrics, voice/reference settings, music choices and duration policy. Unknown keys, payment fields, raw source URLs and provider overrides are rejected. References carry exact `ToolAssetRef` identities under distinct `source_video` and `voice_sample` roles. Structural validation is not ownership verification; the prepare/confirm services must resolve originals and source facts on the server.

`audio-capabilities.ts` projects the seven real packs (five creative intents plus the two existing video soundtrack packs), factual provider models, option constants and current configuration checks. High quality remains unavailable. No network call or quote/debit is performed by discovery. Its revision changes with the projected contract/configuration and contains no credentials. Current pricing still comes from the canonical quote owner, not the discovery document.

Exact variant availability matters within a mode. For example, a configured FAL soundtrack route does not make the same route with Lyria music available. Preparation and confirmation match the normalized voice/music settings to an available variant rather than relying on the mode-wide summary.

## Preparation and owned source evidence

`prepare-audio-generation.ts` requires an OAuth principal with both a user ID and client ID, the existing paid-generation gate, and an unrestricted account. It normalizes the strict version-1 request, resolves each `ToolAssetRef`, runs the existing `prepareAudioRun` owner, obtains the current canonical price, checks shared spending controls, and inserts an expiring wallet quote. It returns exact cents/currency, expiry, balance before/after, top-up need and `confirmationRequired: true`. It creates no job or charge and never calls the generation executor.

`audio-reference-assets.ts` resolves `asset` identities from a ready, undeleted owned library row and `job-output` identities from the exact owned output of a completed visible job. It selects the stored original, not a thumbnail or preview, and records its MIME, dimensions, duration and size facts. Preparation may inspect the owned source video outside a transaction. The quote stores the request hash, exact resolved reference evidence, measured source probe, duration, aspect ratio and account-bound input key under a hashed versioned evidence envelope. Private source URLs remain inside the private quote snapshot.

Confirmation does not probe, download or call a provider while holding the quote transaction. It re-resolves the DB-owned identities and compares the original URL and stored facts exactly with the prepared evidence. Removal, replacement or fact drift invalidates the quote before any debit.

## Quotes and mixed readers

`quote-repository.ts` retains one SQL/state machine. A surface codec supplies strict normalization, hashing and funding interpretation. The SQL surface predicate applies before owner reads and every individual state mutation. A video/image operation therefore cannot claim or invalidate an Audio row even before its parser runs. Global expiry remains a bounded, shared operation.

The existing exports retain the video/image/trial codec and its authoritative trial checks. `audio-quote-repository.ts` exposes a wallet-only Audio codec and a strict union reader for top-up/recovery. Audio funding snapshots must match stored cents and currency. Mixed activity labels the actual Audio tool; top-up keeps the existing signed payload, invalidates the old quote, and directs fresh Audio preparation/confirmation after funding.

## Reservation and execution

`audio-run-reservation.ts` builds the initial job and trusted in-process execution context from a server-prepared run. `createInitialAudioJobInExecutor` composes the existing wallet/job insertion with a caller's transaction. The web route still prepares and checks its current expected price before its reservation transaction, then invokes the same `executeReservedAudioRun`. That executor never reserves a second charge.

`confirm-audio-generation.ts` accepts exactly `{ quoteId, confirmed: true }` from the same OAuth user/client. It locks the Audio quote and treats claimed, accepted and failed states as replay states tied to their durable job. For a prepared quote it rechecks expiry, account restriction, exact request hash, exact catalogue and variant availability, evidence integrity, current pricing policy, reference identity and the shared confirmation spending total. Pricing rules are read through the transaction executor; media and provider work are absent from the transaction. `buildAudioRunReservation`, `createInitialAudioJobInExecutor`, and the Audio quote claim then commit the initial job, wallet debit and claim atomically.

Only the transaction winner calls `executeReservedAudioRun`, after commit. Concurrent and later confirmations read the stored Audio job status and cannot submit again, including after completion, failure or refund. A failed executor marks the quote failed after the Audio runner has persisted its failure/refund state. Failure to project a successfully completed claim from `claimed` to `accepted` is logged for reconciliation and never rewrites the quote as failed; replay still follows the durable completed job.

The retained synchronous limitation is deliberate: a process crash after the committed claim and before or during provider submission leaves a durable claimed job for status/manual reconciliation, but it is not permission to restart the provider automatically. A fresh execution requires a fresh prepared quote and explicit approval. The existing top-up handoff invalidates an underfunded Audio quote and directs the assistant back through `prepare_audio_generation`; funding never revives the old approval.

Every shared wallet reservation now locks the account's oldest immutable receipt before it calculates the balance and inserts a charge. This real per-user row provides collision-free serialization between distinct video, image, Audio and tool jobs; the balance query runs as a following statement so `READ COMMITTED` observes a competing committed debit. An account without any receipt cannot fund a positive reservation. Standalone callers open this transaction once, while `reserveWalletChargeInExecutor` composes with the caller's existing transaction and never opens a nested transaction.

Audio provider failure first persists `status=failed` with the existing `payment_status=paid_wallet`. In this state the provider failure remains visible and the still-present debit is explicitly recoverable by reconciliation. The refund owner then locks the exact Audio job and its single persisted charge, rejects owner/surface/job/amount/currency/product/snapshot inconsistencies, and inserts an idempotent refund using only the charge row. It changes the job to `refunded_wallet` only after the exact refund exists and matches. Any insert or status-transition failure rolls back the refund transaction and leaves `failed` plus `paid_wallet`; the runner reports both the provider failure and that wallet reconciliation is pending. Replaying that reconciliation is safe and never restores the creative authorization.

Audio progress and terminal writes are conditional on the job still being `pending` or `running` with `paid_wallet`. Completion and failure use named helpers that return whether their atomic update won. The runner must observe a winning completion before it projects `job_outputs` or returns a completed response, and it must observe a winning failure before it starts refund reconciliation. A completion waiting behind a refund therefore cannot overwrite `failed/refunded_wallet`; a late failure cannot overwrite `completed/paid_wallet`; and late progress cannot reopen either terminal state. A pre-existing `refunded_wallet` value is replayable only when its exact refund receipt already exists.

The historical `app_jobs.duration_sec` contract is integer and non-null. Unknown song duration starts at zero in that column; it is not an output estimate. Completion stores the ceiling integer there and the exact probe value in `settings_snapshot.measuredDurationSec`, `settings_snapshot.mediaFacts` and the response. The original audio file remains untrimmed. Downstream timeline code must consume verified original-media facts, not this rounded column.

Standalone persistence recognizes WAV only with its RIFF/WAVE signature, FLAC, Ogg, and MP3 with a valid ID3 header or MPEG audio frame header. Analyzable bytes in any unknown container are rejected before upload.

## Public MCP registration and results

`mcp-publication.json` owns the separate `audioGeneration` kill switch and keeps it false by default. Audio tools register only when both `paidGeneration` and `audioGeneration` are effective. The HTTP runtime applies the same conjunction and its audit allowlist recognizes the three exact names without retaining arguments. `list_audio_capabilities` is read-only and closed-world; preparation is non-destructive and closed-world; confirmation is destructive, idempotent and open-world because it can debit the wallet and invoke a provider after the reservation commits. Each adapter passes the authenticated OAuth user/client identity into its qualified service and rejects extra input keys.

Completed Audio recovery continues to read the owned `app_jobs` state machine. Status and recent-generation readers classify `surface=audio`, prefer the stable original Audio URL and fall back to the legacy `video_url` column used by soundtrack packs while preserving the Audio surface and exact persisted MIME type. They project decimal `settings_snapshot.mediaFacts.durationSec` or `measuredDurationSec`. `job_outputs` remains the durable download record: completion upserts the original at `(job_id, kind, position)`, stores its byte-derived MIME type, the ceiling database duration and the decimal measured duration in metadata. Replaying the projection cannot duplicate the output. Result resources, the native Audio reader and signed-download filenames all preserve that durable Audio MIME even when the original came from the legacy column. No schema migration is required.

The current MCP App is the immutable `generation-result-v5.html`; legacy v1-v4 resources continue to serve the v4 document. Version 5 adds only the Audio result behavior. Pending and failed results never receive a media source. A completed result renders a compact editorial header and native manual `<audio controls>` without autoplay, shows measured duration and provides Download, Reuse settings and Open in MaxVideoAI actions. Reuse builds only an allowlisted `/app/audio?job=…&reuse=1` destination from the owned workspace URL. Mobile actions keep 44-pixel targets with Open on a full-width second row. Light, dark and 390-pixel fixtures are captured through `scripts/qa/render-mcp-audio-result.ts`.

The shared `job_outputs` upsert requires the same `(job_id,user_id)` in `app_jobs`, permits conflict updates only for the same output owner and fails on an ownership mismatch; video and image callers use the same guard.

For soundtrack results that contain both an Audio original and a rendered video, non-App recovery returns both resources: the Audio link keeps the persisted Audio MIME and the video link uses its video MIME. Audio-only and legacy video-column-only results retain their single-resource behavior, and canonical duplicate URLs remain collapsed.

Standalone original persistence recognizes WAV, FLAC, Ogg and MP3 from the bytes. MP3 requires a valid ID3 header or MPEG audio frame header; an analyzable stream with an unknown container is rejected before upload.
