# Médiathèque : inventaire de parité avant intégration

Audit statique du 9 novembre 2026, branche `codex/media-library-prototype`, HEAD `5135e4e2b7ad04261d26b3f7669eb2ec8aded1db`. Sources de l’application et du prototype examinées ; aucun accès navigateur, base ou production, aucune exécution de génération ni mutation métier. Les tests cités ont été lus ou repérés, **pas exécutés**. Le document décrit le code de ce checkout, pas une vérification de la production déployée.

La direction visuelle peut être reprise, mais le prototype n’est pas un contrôleur métier de remplacement. L’application possède déjà l’audio, des sorties récentes distinctes des médias enregistrés, des sauvegardes par sortie, des lectures privées, le partage vidéo et plusieurs parcours de réutilisation. Favoris, collections, corbeille restaurable, tri configurable et sélection multiple de gestion sont des ajouts du prototype.

## Fonctions nouvelles à ne pas décrire comme déjà persistantes

- **Favoris** : ni champ ni action favoris dans `Browser:26–46` / `Page:330–393`. Le prototype stocke des overrides React (`Prototype:19,93,144`), perdus au reload. Le raccorder impose une politique owned, un write durable, filtre/tri/pagination cohérents et rollback d’erreur.
- **Collections** : aucune collection Library dans les contrats inspectés ; `Prototype:20–21,110–117,128–131` crée des regroupements locaux. Les projets réellement existants sont les films Studio (`Studio:73,112`), avec d’autres règles et mutations. Ne pas réutiliser leurs IDs comme des collectionIds.
- **Sélection multiple de gestion**, sélection globale, opérations groupées, corbeille/restore, tri nom/ancien, vue tous types, densité : fonctions visibles du prototype (`Prototype:23,26–28,140–151`). La sélection multiple immédiate de certains **pickers** existe déjà (`Picker:18–21,38,109`), mais ce n’est pas une API batch de la Library.
- **Renommer un média** : aucun contrôle de renommage dans la page ni le prototype audités ; le nom affiché peut provenir de métadonnées existantes. Un inspecteur éditable constituerait un ajout, pas une parité acquise.

## Anomalies et obstacles concrets

1. **Identité canonique perdue avant Studio (blocage existant).** `AssetsAPI:61–64` fournit l’id interne et `assetId/ref` dérivés de publicId. `Data:115–140` omet ces champs ; `Destinations:76` tente de recréer la ref à partir de `asset.id`. Or `frontend/lib/media-identity.ts:19–21` accepte uniquement `ma_` + 32 hex, tandis que `frontend/server/media-library-records.ts:318–319,363` produit des IDs internes `output:…`/`url:…`. Un upload sans jobId n’obtient donc pas Studio via `Destinations:77–81`. Le test `media-destination-actions-dom:15` injecte directement un `ma_…` comme id et masque ce cas. L’adaptateur doit garder **id de mutation** et **ref canonique** distincts ; ajouter un test API→Data→Destinations avec un vrai couple d’IDs.
2. **Durée/facts de médias enregistrés perdus.** `AssetsAPI:64,74` renvoie mediaFacts et durationSec, mais `Data:115–140` ne copie ni l’un ni l’autre. `Panel:57` ne peut donc pas afficher la durée enregistrée ; l’éligibilité de continuation reçoit aussi moins de faits (`Destinations:23–24`). Les récents conservent durationSec (`Data:154`). Préserver facts mesurés et inconnu explicite dans l’adaptateur ; aucune durée ne doit être reconstruite depuis un réglage demandé.
3. **Delete proposé aux legacy-only qui ne sont pas supprimables par cet owner.** `Listing:294–295` expose `user_assets.asset_id` sans publicId ; `Data:135` marque tous les saved canDelete, et `Page:380` propose Delete sans autre gate. `Deletion:23–32` exige une row media_assets et renvoie not_found sinon. Il faut décider un chemin compatible owned pour ces lignes, ou rendre la restriction explicite ; un retrait local de la grille ne résout pas l’échec serveur.
4. **Pas de données pour un inspecteur génération complet dans le DTO de listing.** `RecentAPI:86–108`, `AssetsAPI:60–79` et les types `Browser:26–46` n’apportent pas le modèle, prompt et snapshot complet. `Gallery:21–29` les obtient d’un autre contexte. Avant un nouvel inspecteur Library riche, identifier son owner de lecture exacte par job/output ; garder les liens source existants. L’audio est même explicitement privé de ce lien par `Page:241`, malgré le helper audio `Helpers:350–351` : gap actuel à qualifier, pas fonction déjà offerte.
5. **Le même champ preview ne peut servir tous les rôles.** Le prototype choisit `previewUrl` pour image, vidéo et audio (`ProtoViewer:25–32`) ; en réel preview vidéo peut être un extrait silencieux basse qualité. Le lecteur réel choisit playback/original (`Panel:35–38`) et download original. Rebrancher simplement les DTO dans le viewer produirait une inspection dégradée et pourrait télécharger une URL privée sans transport adapté (`ProtoViewer:198`).
6. **La sauvegarde récente, le partage et Draft disparaissent si le viewer est remplacé tel quel.** `ProtoViewer:194–202` ne connaît que original/use/trash ; `prototype/src/types.ts:5–22` ne porte ni jobId/outputId, isSaved, grants, facts, Draft ni callbacks de partage. Ces données et points d’extension doivent être explicites avant toute substitution de Panel.
7. **Pagination globale et nouveaux contrôles d’organisation restent à concevoir.** Le prototype connaît ses 1 000/10 000 objets avant de filtrer/trier/sélectionner (`Prototype:12,16,54–67,143`). L’application n’a que des pages de 30 et aucun total global (`Helpers:228`, `AssetsAPI:81–82`). Les tris et « tout sélectionner » ne doivent pas agir silencieusement sur les seules lignes chargées ; favoris/collections/trash ne peuvent être des filtres locaux prétendant couvrir le compte.

## Première tranche d’intégration recommandée

1. Reprendre la **présentation page** (toolbar, grille compacte virtualisable, disposition audio) au-dessus des owners actuels `useLibraryPageData` / `useLibraryAssetMutations`. Conserver filtres réels, recent/saved, recherche serveur, pagination, import et shell i18n ; mettre de côté les contrôles nouveaux sans persistance.
2. Définir une projection de présentation qui conserve id interne, ref publique/job-output, source, original/thumbnail/preview/playback, grants, measured facts, provenance job/output, saved state et callbacks. Corriger explicitement les pertes d’identité/durée dans ce raccord avec des tests d’intégration DOM réalistes.
3. Garder d’abord **MediaActionPanel + MediaDestinationActions + VideoSharePanel + Draft + Studio** comme contenu/action owners ; intégrer progressivement le cadre visuel et la navigation du prototype autour d’eux. Ne pas changer en même temps les pickers de tous les outils.
4. Valider la parité sur images/vidéos/audio, uploaded/generated/recent/tool/legacy, compte A→B, read grants, original download, Save/Delete, source reuse, Extend/Modify, Studio et Draft. Les nouveaux favoris/collections/trash/batch import feront ensuite des tranches métier séparées avec leurs contrats.

**Résumé :** audio et projets Studio sont réels ; collections/favoris/corbeille restaurable de Library sont simulés. La tranche sûre est le nouveau navigateur visuel sur les données/actions existantes, avec une projection complète des identités et URLs, puis le lecteur. Le principal risque de régression est une belle grille qui perd silencieusement les actions métier et la distinction entre original, preview et accès privé.
